## Findings

### [confirmed · critical] Seed embeds playerRowId, so How Many?/Swipe Sort/Pairs are not actually shared-per-round as documented

- **Id:** `G3-3` (track G3) · **Game:** how_many · **Where:** `src/player/PlayerApp.tsx:250`
- **Expected:** All players in the same round see the identical How Many? fields/counts, Swipe Sort colour sequence and Pairs layout, per ADR-134(2)/ADR-136 and the game docs — the seed used for content generation should be keyed only by `round.id` (or `round.id` + flash/item index), never by `playerRowId`.
- **Actual:** Each player's `GameProps.seed` is `${round.id}:${playerRowId}`, so `fieldFor`/`layoutFor`/Swipe Sort's colour draw produce a genuinely different sequence per player in the same round. With a typical booth crowd of 5-8 players, `howManyStrips.ts`'s `modeOf(true_counts)` (src/host/howManyStrips.ts:57-69) is picking a plurality out of mostly-distinct random values — the "true count" shown on the big screen is close to arbitrary rather than a real shared ground truth, and the axis center a viewer sees may not match what they themselves were shown on their phone.
- **Evidence:** src/player/PlayerApp.tsx:250 sets `seed: \`${round.id}:${playerRowId}\`` unconditionally for every game (no per-game branch), and this is the exact string passed straight through to `GameProps.seed` (src/player/PlayerApp.tsx:355, src/player/screens.tsx:275). src/games/how-many/field.ts:55 then does `new Rng(\`${seed}:hm:round${index}\`)` — since `seed` already contains the caller's own `playerRowId`, every player in the same round gets an independently-random `Rng`, hence a different `N_i` (true_count) per flash, and by the same mechanism a different Swipe Sort colour sequence (`ss:item${k}`) and a different Pairs layout (`pr:layout`). This contradicts three separate doc statements: docs/games/how-many.md:25 ("Everyone in a round sees the same three fields; a reload computes the same ones again"), docs/plans/games-v3.md:17 ("...keyed by content position..., so everyone in the round sees the same content...") and docs/plans/games-v3.md:362 (Pairs: "The whole session sees the same board"). It also contradicts the host reveal's own assumption in src/host/howManyStrips.ts:52-56 ("The most common value (everyone shares the round's seed, so one tampered row can't move the axis)").
- **Suggested fix:** In src/player/PlayerApp.tsx:250, change the seed assigned on beginning a round to be keyed only by round content (e.g. `round.id`), not `playerRowId`. If a per-player component is still needed for some other game's randomness (e.g. Trivia's per-player option shuffle, which is documented as intentionally per-player per ADR-027), that should be layered by the specific game module reading `playerRowId` itself from context, not baked into the shared `GameProps.seed` used by every game.
- **Verifier:** src/player/PlayerApp.tsx:250 stores `seed: `${round.id}:${playerRowId}`` for every game when a round begins, and line 355 uses the same string as the fallback. That value reaches GameProps.seed unchanged. The three new games key all their content off it: how-many/field.ts:55 `Rng(`${seed}:hm:round${index}`)`, pairs/layout.ts:20 `Rng(`${seed}:pr:layout`)`, and Swipe Sort `ss:item<k>`. So each player in a round gets different How Many? counts, a different Pairs board and a different Swipe Sort colour sequence. The docs say the content is shared per round: how-many.md:25 ('Everyone in a round sees the same three fields'), pairs.md and games-v3 ('the whole session sees the same board'), swipe-sort.md:23, SESSION_LIFECYCLE.md:129 ('per-round random seed') and types.ts:42 ('Per-round seed'). Nothing in src/games strips the player part. On the host, howManyStrips.modeOf assumes a shared seed. With distinct true_counts, every value appears once, so the tie rule makes the axis the top-ranked row's count. Everyone else's dot is then placed relative to a count they never saw.
- **Verifier corrections:** The scope is wider than the three new games. ADR-134(2) says 'seeding already exists per round', which is also wrong: Close the Brackets (`cb:L<L>:<k>`), Color Clash (`cc:trial<k>`) and Odd One Out are per-player today, against their own docs. The fix must keep the Trivia draw per player if that is intended (ADR-027: 5 of 30 per player, 'per-player draws happen on the phone', ADR-116). It can do that by keeping a per-player component only for Trivia, or by deciding explicitly that Trivia shares too. Changing the seed changes what a phone reloading mid-round sees: phones that already stored `local.seed` keep the old value, which is fine, but do not deploy this during an event. The line numbers (250, 355) are correct.

### [confirmed · critical] A host reload during the How Many? round_board step guarantees the reveal (dots and the crowd-average marker) is cut off before it finishes

- **Id:** `G3-2` (track G3) · **Game:** how_many · **Where:** `src/host/HowManyReveal.tsx:33`
- **Expected:** A host reload mid-step should resume the reveal at (roughly) the same point in its 0-7000 ms timeline it would have reached without the reload, so guests still see the complete picture (dots + crowd average) before the step ends, matching ADR-129's intent that a reload lands on the same step without breaking what's shown.
- **Actual:** The reveal component has no way to resume mid-animation: every reload restarts its internal 0→5800 ms schedule from zero while the outer step clock keeps counting down the real elapsed time since `ended_at`. For any reload happening more than ~1200 ms into the round_board step (verified against the code's own constants, at zero network latency), the crowd-average marker mathematically cannot finish its fade-in before `StepFade` crossfades the stage to the session-total board (src/host/Intermission.tsx:264, `stepKey={isTotal ? 'total' : 'board'}` triggers on `state.step` change, unmounting `Reveal`); a reload past ~2000 ms guarantees even the dot bursts themselves don't finish, and any nonzero `fetchRoundReveal` latency (which is unavoidable) tightens this further. This matches the reported "time things" symptom for How Many? directly.
- **Evidence:** Timeline computation from code constants: schedule.ts's `intermissionState()` (src/host/schedule.ts:50-67) is correctly a pure function of `endedAtMs`/`nowMs`, so a reload lands on the right *step* with the right *remaining budget* — e.g. a reload 2 s into the 7000 ms round_board step (INTERMISSION_ROUND_BOARD_MS, src/config.ts:33) leaves exactly 5000 ms of step budget. But `HowManyReveal` (src/host/HowManyReveal.tsx:32-34) fully remounts on that reload (`useRoundReveal`, src/host/reveal.ts:130-146, always re-fetches on mount, no cache across remounts), and every dot's entrance animation is scheduled by `ShatterBurst`'s `delay` prop, which is explicitly "ms after mount" (src/effects/shatter/ShatterBurst.tsx:8-9, `useReplay(trigger, playOnMount, ...)` fires on mount). The dot-burst schedule (`revealSchedule`, src/effects/shatter/plays.ts:454-475) needs the full 5000 ms (`STC_REVEAL_TIMELINE.totalMs`, src/effects/shatter/motion.ts:85) from that new mount, and the crowd-average marker needs 5200 ms + a ~600 ms fade (`HM_REVEAL_MEAN_MS`, src/config.ts:56; burstMs, src/effects/shatter/motion.ts:86) = 5800 ms from that mount — before even counting the unavoidable `fetchRoundReveal` network round trip that must resolve before any of this starts (src/host/reveal.ts:133-144). So the reveal needs ≥5800 ms of real time from the reload, against only 5000 ms of step budget remaining (2000 ms case) — a 800 ms deficit with zero network latency, worse with any real fetch latency.
- **Suggested fix:** Anchor the reveal's own animation schedule to the same `ended_at`-relative clock the step uses (pass the intermission's `endedAtMs`/server offset into HowManyReveal/StcReveal and compute each dot's/marker's absolute target time instead of a mount-relative `delay`), so a reload (or any fetch latency) shortens the animation's lead-in but the finale still lands at the same absolute time. Alternatively, shrink `HM_REVEAL_MEAN_MS` and the dot-burst budget so the whole reveal reliably finishes well inside the 7 s step even after a worst-case fetch/reload delay, and treat this same fix as applying to StcReveal (which has the identical mount-relative-vs-ended_at-anchored structural mismatch, just with more slack today).
- **Verifier:** The mechanism is real. intermissionState (schedule.ts:50-67) anchors the step on endedAtMs, so after a host reload the round_board step keeps only its remaining time. HowManyReveal remounts, and useRoundReveal refetches after mount. Every dot and the mean marker use ShatterBurst/playBurst `delayMs`, which counts from mount (ShatterBurst.tsx:8, plays.ts:389). The dots end at 5000 ms after mount (revealSchedule over STC_REVEAL_TIMELINE.totalMs). The marker starts at HM_REVEAL_MEAN_MS = 5200. When the step changes to session_total, layout becomes 'split' and the Reveal unmounts. So a reload far enough into the 7 s step cuts off the marker, and later the last dots. The reload also adds the host's own startup (auth, load, server offset) on top of the reveal fetch.
- **Verifier corrections:** The numbers are a little off. With shards = 0 the marker fades in over burstMs/2 = 300 ms (plays.ts:392), not about 600 ms, so it is fully in at 5500 ms after mount. At zero latency the marker is cut if the reload lands more than about 1.5 s into the step, never appears past about 1.8 s, and the last dots are cut past about 2.0 s. Host startup and fetch latency shift those thresholds earlier. Severity is overstated: this needs a host reload or a second host tab during the 7 s round-board step (E8/E23), which is rare. ADR-129 only promises the same step, not the same point in the animation. StcReveal has the same structure (its dots end at 5 s). There is no evidence this is the 'time things' symptom Talal reported; that more likely comes from G3-3 or phone-side timing. Medium/low, not critical.

### [confirmed · critical] Round seed is composed per-player (`${round.id}:${playerRowId}`), breaking the documented "everyone in the round sees the same content" contract for 6+ games — most severely the How Many? host reveal

- **Id:** `G4-1` (track G4) · **Game:** how_many, pairs, swipe_sort, close_brackets, color_clash, simon, odd_one_out · **Where:** `src/player/PlayerApp.tsx:250`
- **Expected:** Every player in the same round should compute the same `N_i`/board/sequence/openers from the shared seed (per docs above), so the How Many? reveal's `modeOf(true_count)` finds a real, near-unanimous consensus and Pairs/Swipe Sort/Close Brackets/Color Clash give every player in a round the same content.
- **Actual:** `seed` folds in `playerRowId`, so each player's `Rng` stream — and therefore their true counts, board layout, item sequence and bracket sequence — is unique to them, not shared with the room.
- **Evidence:** src/player/PlayerApp.tsx:250 sets `seed: \`${round.id}:${playerRowId}\`` when a round begins, and line 355's fallback repeats the same composition (`local.seed ?? \`${view.round.id}:${playerRowId}\``). This value is handed straight to every game as `GameProps.seed` and each game keys its `Rng` off it verbatim (e.g. `src/games/how-many/field.ts:55` `new Rng(\`${seed}:hm:round${index}\`)`, `src/games/pairs/layout.ts:20` `new Rng(\`${seed}:pr:layout\`)`, `src/games/swipe-sort/items.ts`, `src/games/close-brackets/sequence.ts`, `src/games/color-clash/trials.ts`, `src/games/simon/sequence.ts` (`generateSimonSequence(seed, …)`), `src/games/odd-one-out/OddOneOut.tsx` (`oddTileIndex(seed, …)`). Since `playerRowId` is unique per player (ADR-006), every player in the same round gets a *different* field/board/sequence, not the shared one every game doc promises: how-many.md:25 "Everyone in a round sees the same three fields"; pairs.md:23 "Everyone in the round gets the same board"; swipe-sort.md:23 "Everyone in a round gets the same sequence"; close-brackets.md:33 "everyone in a round who reaches length 5 for the first time sees the same five openers"; color-clash.md:26 "every player in a round gets the same sequence of (word, ink) pairs". This also contradicts the type contract itself: `src/games/types.ts:42` documents `seed` as "Per-round seed (reload-stable)", `docs/ARCHITECTURE.md:179` "the per-round seed", `docs/SESSION_LIFECYCLE.md:129` "per-round random seed … so a reload shows the same content", and the locked decisions ADR-134 (2) "every game gets the round's seed … so everyone in a round sees the same sequence" and ADR-136 (1) "seeded per round as ADR-134 (2)". Worst concrete breakage: `src/host/howManyStrips.ts:52-68` (`modeOf`) picks the H3 reveal's centre count as "the most common `true_count` across rows" with the comment "everyone shares the round's seed, so one tampered row can't move the axis" (also tested in `src/host/howManyStrips.test.ts:47`). Because every player's `true_count` for a given flash is independently random (a different `N_i` drawn from a different per-player seed), there is normally no real consensus value to find; `modeOf` degenerates to picking whichever count happens to collide by chance (usually none, so it falls back to the first row's own idiosyncratic count with frequency 1). The strips the host projects then centre on a count almost nobody actually saw, so nearly every guess renders as a wild outlier/pinned dot — this matches the user's reported "time things for how many" symptom (the reveal looks broken/nonsensical) even though the root cause is seeding, not timing. Pairs/Swipe Sort/Close Brackets/Color Clash don't have a host reveal, so their breakage is silent unfairness (players get different-difficulty boards/sequences) rather than a visible crash, but it still contradicts their docs; PR-T9/CB-T9/CC-T7/SS-T7 only exercise the pure `layoutFor`/`draw` functions with a hand-picked seed, so none of them catch this — it is only observable through the full PlayerApp integration, which has no test.
- **Suggested fix:** Make `GameProps.seed` purely `round.id` (already a globally-unique UUID: `rounds.id uuid primary key default gen_random_uuid()` — no need to compose with `session.id`/`round_no`). Update both composition sites in `src/player/PlayerApp.tsx` (line 250's effect and line 355's fallback) to `seed: round.id` / `local.seed ?? view.round.id`. Trivia is the one exception (see G4-2) — give it its own per-player component instead of folding one into the shared `seed`, e.g. add an optional `playerId?: string` to `GameProps` (`src/games/types.ts`) populated from the shell's already-tracked `playerRowId`, and have only `src/games/trivia/Trivia.tsx` build `drawTriviaQuestions(pool, \`${seed}:${playerId}\`)`. No other game's source needs to change (they already just consume `seed` as an opaque string); only the value changes. Also guard the localStorage migration: `local.seed` is written once at round-begin and kept verbatim across reloads for that player (ADR-018), so a mid-round deploy would leave players who already started that round on the old `round.id:playerRowId` format while players who join/begin afterward get the new `round.id`-only format — a transient split within one round. Given ADR-032 (no deploys on event day) this is a low-probability dev/dry-run-only edge case, but the planner should decide whether to accept it (documented) or add a version-tagged seed key to detect and discard a stale-format `local.seed` on reload.
- **Verifier:** I checked this in the code. src/player/PlayerApp.tsx:250 persists `seed: `${round.id}:${playerRowId}`` when a round begins. The fallback at :355 builds the same string. playerRowId is the guest's own `players` row id (join payload `player_row_id`, line 113), so it is different for every player.
