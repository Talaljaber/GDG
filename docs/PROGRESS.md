## Session notes

### 2026-09-26: Phase 8 timing fixes
- Root causes, in plain words: (1) the phone built the game seed from the round **and the player**, so every phone drew its own How Many? fields, Pairs board and Swipe Sort sequence, and the big screen compared everyone against numbers they never saw; (2) How Many? started each step when the previous timer happened to fire, so a reload, lock or hidden tab pushed the rest of the round later; (3) Pairs timed the clear with a clock that stops while the phone sleeps, and had no return handler; (4) the big-screen reveal counted from when it mounted, not from when the round ended, so the crowd average was on screen for about a second or not at all; (5) a round ended during the 3-2-1 still mounted the game and sent a 0.
- Team calls (Talal, 2026-09-26): How Many? keeps its fixed schedule (flashes shown while hidden are lost, the round still ends inside 39 s); the Swipe Sort gap-press change was dropped.
- Integration: the saved investigation probes under `docs/investigations/` were being collected by Vitest and ESLint; both now skip them. No migration (the bounds are unchanged).
- e2e: the first full run failed `phase1` (the last Stop the Clock finisher's P7 had already moved to P8 before its result rows were checked) and then `E2E-1` (its cleanup started from the round `phase1` left behind); a single `phase1` rerun failed the 2 s join-latency check (2973 ms). The machine was at 100 % CPU from unrelated processes; the second full run passed 9/9 with no code change. Both checks are timing races worth hardening if they recur (not changed here).
